# Only Good Antibodies

The code behind [onlygoodantibodies.co.uk](https://onlygoodantibodies.co.uk) —
a public record of how commercial antibodies performed when tested against
knockout controls, and the lab platform that produces it.

Antibodies that do not do what their label says are a large, quiet source of
irreproducible biology. Only Good Antibodies publishes the results of testing
them properly: each reagent tried against a knockout cell line, in the
applications people actually use it for, with the figure that shows the result.
Only Good Antibodies and [YCharOS Inc.](https://ycharos.com) run this work
together.

Everything here is open — the code, and the characterisation data it
publishes.

## What is in this repository

A Django project with three applications:

| | |
|---|---|
| `core` | The public website, the data portal, and the public API |
| `academy` | Antibody validation e-learning and user accounts |
| `pipeline` | The lab platform: reagents, cell lines, experimental sessions, figure review and publication |

Plus two reader-facing tools that ship from the same repository:

| | |
|---|---|
| `browser-extension/` | Marks antibodies on a publisher's page with their per-application verdict |
| `mcp_servers/` | Answers the same questions for a model reading a paper, plus a controls assessment |

## Getting the data

You do not need this repository to use the data. It is served from the site:

- **Data portal** — browse, filter and download in a browser
- **Public API** — documented at [/data-access/api/](https://onlygoodantibodies.co.uk/data-access/api/)
- **Browser extension** and **MCP server**, for reading papers

Start at [/data-access/](https://onlygoodantibodies.co.uk/data-access/).

This repository holds the code and a few published data artefacts (the citation
index, the extension's dataset). It does not hold the full characterisation
database or the figure images — those are served from the site and from object
storage.

## Running it locally

Python is pinned in `.python-version` (3.11).

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install pytest            # deliberately not in requirements.txt
python manage.py migrate --database=pipeline_db
python manage.py migrate --database=academy_db
python manage.py runserver
```

**Migrate each database by name.** There are two, split by subject (see
`OGA_website/db_router.py`): `pipeline_db` holds the antibody and scientific
data, `academy_db` holds people and organisations. A bare `manage.py migrate`
targets `default`, which is deliberately empty — nothing is routed there, so an
alias with no engine makes an unrouted access raise instead of quietly reading
or writing somewhere plausible.

Locally the pipeline database falls back to SQLite unless
`PIPELINE_DATABASE_URL` is set, so a local checkout has no production data —
which is the intended behaviour, not a setup step you have missed. `academy_db`
falls back the same way without `ACADEMY_DATABASE_URL`.

Configuration is environment-driven; there are no secrets in this repository.
See `.env.example` for the variables the site reads.

### Tests

```bash
python manage.py test pipeline core academy credentials selector
python -m pytest pipeline/services/tests pipeline/services/cropper/tests -q
```

Two runners, deliberately. Django's runner collects only `unittest.TestCase`
subclasses, and every module under `pipeline/services/tests/` is pytest-style, so
neither runner sees all of the tests. Both commands are what CI runs; see
`.github/workflows/`.

The apps are named rather than left to discovery because a bare `manage.py test`
walks into `mcp_servers/tests/`, which is pytest-only and needs its own
dependencies, and reports four import errors on an otherwise-clean run. To run
that third suite:

```bash
pip install -r mcp_servers/requirements.txt
python -m pytest mcp_servers/tests -q
```

Browser tests need Playwright and Chromium, and skip without them.

## About this snapshot

This is a curated snapshot of a private working repository, published as its own
history. It is generated by an export that classifies every file explicitly, so
what is here is here on purpose.

It is a point-in-time copy rather than a live mirror, so it can trail the
deployed site. Where the two disagree, the live site is authoritative.

Development happens against internal working documents — `CLAUDE.md`,
`DECISIONS.md`, `PLATFORM_ROADMAP.md` and a few design notes — which are not
published. Code comments and the occasional README still cite them, so you will
see references here to files that are not in this repository. Nothing you need
in order to read, run or reuse the code lives in them; they are a project diary,
and they name people and unreleased work, which is why they stay behind.
