Impact

What the site has recorded people doing

Every figure here is something the application wrote down because a person did it — a request served, a certificate issued, a plan recorded. Assembled from four apps that each kept their own count, so a report or a grant can quote one page instead of four admin screens.

{% comment %} Said first, and deliberately not in small print at the bottom. This page has no visitor numbers in it and never will — those live in Cloudflare — and a reader who takes these totals for traffic will read them as far too small and conclude the site is unused. Naming the gap is the difference between a narrow number and a wrong one. {% endcomment %}

This is not traffic. Django records no page views, visitors or referrers — those are in Cloudflare, which is a different account and a different question. What is below is the narrower and harder number: someone finished a lesson, built a plan, pulled the API. Read it as reach and engagement, never as how many people saw the site.

Browser-extension installs are not here either. The extension fetches two files a day, which was the nearest thing to an install count until Cloudflare began caching them at the edge on 30 Aug 2026 — so what reaches this site now is whatever the edge did not absorb, and charting it would draw the fix as a collapse in usage. Cloudflare's own analytics is where that question goes.

A client is software, not a person. It is what the connecting app calls itself — claude-ai, claude-code, chatgpt. The server knows who signed in and deliberately never sends that here, so this counts reach and holds no identities. A call is a question asked. It is counted before the tool runs, so a call that then failed is in these totals. That is the honest direction for a usage number and the wrong one for a reliability number, which this is not. {% if mcp.internal_calls %} {{ mcp.internal_calls }} of our own call{{ mcp.internal_calls|pluralize }} {{ mcp.internal_calls|pluralize:"is,are" }} excluded from everything above. The connector marks a call as ours by matching the caller against a list of our own sign-ins and sending a yes-or-no — it never sends who, so this page can hold the distinction without holding an identity. A call it cannot place counts as somebody else's. {% endif %} Only the hosted server reports. Anyone running the connector locally over stdio is invisible here, as is every call made before {{ mcp.first_seen|date:"j M Y"|default:"reporting was switched on" }}. Days in is the number to quote. The portal reconnects itself whenever the tab is reloaded, so connects counts reloads, and a key shared inside one company counts as one organisation however many people use it. Dates, not times. The counter keeps one row per organisation per day so that its size is set by who holds a key rather than by how hard anyone pulls — which buys the dates and gives up the clock. There is no “signed in at 14:03” here. Last API call is any request, sign-in or not. Far ahead of last in means a script that still syncs for an organisation whose people have stopped opening the portal — which neither number shows on its own. {% if portal.internal_connects %} {{ portal.internal_connects }} connect{{ portal.internal_connects|pluralize }} on internal keys — ours, testing the portal — {{ portal.internal_connects|pluralize:"is,are" }} not in the figures above. {% endif %} {% if portal.refused %} {{ portal.refused }} sign-in attempt{{ portal.refused|pluralize }} carried no usable key — missing, unknown, or belonging to a key that has been switched off. A refused attempt cannot be attributed, by design: the row is keyed on a caller the request failed to identify. So it is a total and never a name, and it is here because “somebody is trying with a key that no longer works” is a support question that would otherwise be invisible. {% endif %}
